# Проверки по риску изменений

Оркестратор использует эту политику для предварительной оценки, ревьюер — для независимого выбора и запуска проверок. Учитывать явные требования пользователя и обязательные проверки проекта.

## Классификация

Выбирать уровень по возможным последствиям и области влияния, а не по числу строк или расширению файла. Для смешанного diff применять самый высокий обоснованный уровень к затронутой области. Однострочная проверка прав доступа может быть R3; большой текстовый документ — R0.

| Уровень | Признаки | Минимально достаточная проверка |
| --- | --- | --- |
| R0 — без изменения поведения | Обычный текст документации, комментарии, опечатки; не исполняемые примеры и не инструкции агента/сборки. | Проверить diff и смысл; при необходимости ссылки или форматирование изменённых файлов. Не запускать runtime-тесты и не писать новые тесты на текст. |
| R1 — локальное изменение | Ограниченная функция, изолированный компонент, CSS или простое UI-поведение; понятны прямые потребители. | Целевые существующие тесты или воспроизведение изменённого сценария. Для поведения — основной путь и относящийся к изменению пограничный/ошибочный случай. Для CSS — визуальная проверка затронутого экрана/состояния; для интерактивности также действие пользователя. Локальные lint/typecheck, если полезны и поддерживаются. |
| R2 — взаимодействие модулей | API-контракт, несколько модулей, общее состояние, локализованное изменение зависимости или конфигурации выполнения. | Целевые unit-тесты и интеграционные/контрактные проверки границ. Проверить изменённых производителей/потребителей. При необходимости один затронутый пользовательский сценарий, сборка или проверка типов соответствующего пакета. |
| R3 — сквозное или критичное изменение | Аутентификация и права, деньги, целостность данных, миграции, широко используемая основа, глобальный runtime/build/test-конфиг или существенное обновление зависимости. | Проверить ключевые инварианты, негативные случаи и затронутые интеграции. Для миграции — совместимость и сохранность данных в изолированной тестовой БД. Расширять до набора подсистемы или полного регресса по критериям ниже. |

R3 не означает автоматически «все тесты репозитория». Узкое исправление авторизации может требовать полного набора auth/permissions и затронутых сценариев, не всех UI-тестов. Изменения инструкций агента, CI и тестов оценивать по их реальному влиянию; успешный запуск с нулём выбранных тестов не считается проверкой.

## Когда нужен полный регресс

Обосновать его хотя бы одним признаком:

- Пользователь прямо запросил полный регресс либо он обязателен для текущего этапа по инструкциям проекта.
- Изменена общая основа/конфигурация/зависимость, влияние распространяется на большую часть системы, а надёжного набора затронутых тестов нет.
- Целевые проверки выявили признаки регрессий за пределами ожидаемой области или границы влияния не удалось установить после разумного исследования.

Если весь существующий набор мал и быстрее/проще запускается целиком, чем выделяется поднабор, допустим один полный запуск с кратким объяснением. Не добавлять к нему автоматически все браузеры, платформы и варианты окружения.

Под полным регрессом понимать применимый набор проверок проекта/CI. Для изменения сборки или транспилятора включать реальную production-сборку локально или в тестовой среде: unit-тесты могут использовать другой транспилятор. Сам деплой из этого требования не следует.

## Выполнение и время

1. Найти реальные команды проекта в его инструкциях, манифестах и CI. Проверить, что выбранная команда действительно ограничивает набор тестов; не угадывать флаги и не называть глобальную команду точечной. Перед shell-командой, которая запускает сервисы, миграции или обращается к сети, установить её реальные побочные эффекты. Использовать локальные тестовые данные/имитации; изменение production-состояния не входит в обычный запуск тестов.
2. Получить быстрый целевой сигнал. Примерный ориентир — первые несколько минут, но это не таймаут и не основание пропускать нужную проверку. Для долгой проверки объяснить цель и ожидаемую длительность, если она известна. Ограничение времени пользователя соблюдать; непроверенное назвать явно.
3. Ревьюер сам запускает ключевую проверку изменённого поведения. Для остальных наборов можно использовать достоверный результат разработчика или CI, если проверены та же версия релевантных файлов, команда, конфигурация и среда. Не повторять весь набор только ради второго запуска другим агентом. Создание дополнительных тестов оправдано реальным риском/багом и ценностью для будущих изменений; не создавать тесты, зеркалящие реализацию.
4. После правок повторять упавшие тесты и проверки новой затронутой области. Расширять набор при новых изменениях, ошибках, изменении окружения или обнаруженных зависимостях. Не прогонять полный регресс после каждого локального замечания.
5. После успешного достаточного набора остановить проверки. При падении отличить ошибку изменения от существующей ошибки, проблемы среды или нестабильности. Повторный запуск требует гипотезы; не перезапускать до случайного зелёного результата и не ослаблять assertions ради прохождения.

В отчёте достаточно уровня риска, команд с фактическим количеством/областью тестов и результатом, причины расширения набора и оставшихся пробелов. Если тесты нельзя выполнить, отдельно сообщить, что проверено чтением кода, а что осталось непроверенным.
